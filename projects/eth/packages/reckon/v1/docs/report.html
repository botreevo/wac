wac-trust: code pinned by hash, trusted by attestation

An experiment building out wac design/system/0016 end to end: Ethereum as the record of what code should run, hashes as the identity of that code, and git and mirrors only as places to fetch bytes from. Built 8 November 2026.

The one-sentence promise. A hash names bytes, and whatever serves those bytes is trusted only to serve them. Whether bytes with a given hash should be installed or run is decided by a policy you write, over statements other people sign. The statements that have to be current, such as names and revocations, are read from an Ethereum chain, and only through storage proofs.

The three layers

Identity

A keccak256 Merkle tree over files: kt1: for a tree, kb1: for one file. It is computed, never stored or trusted, and is the same from a working tree, a git commit or a mirror.

Naming

NAME@0xPUBLISHER in a registry contract. A change is visible at once and only takes effect after the name's delay, so watchers have time to object.

Trust

EIP-712 statements (built, reviewed) signed with ordinary Ethereum keys; revocations and deny lists on chain; and trust.json5, a policy you own.

What wactrust run does

Every step is checked before the next one starts, and the app runs only at the end.

The apps

examples/hello is a command-line module. examples/notes is wac-web's app template, built as one self-contained index.html. Its dependency on wac-web is pinned in wac.lock by tree hash, so the source hash also covers the dependency's bytes.

tools/e2e.sh starts a wacuum devnet and deploys the registry. It builds, rebuilds, reviews, publishes and names both apps, then makes each attack. A check passes only if the outcome is right and the output gives the expected reason.

Findings

In the order I'd act on them.

  1. wac doesn't check the pins. It reads wac.lock with tree, ignores the field, and compiles from a cache entry with one byte changed. Only wactrust lock check catches it, so the check has to move into wac's fetcher and resolver.
  2. The mainnet trust anchor is the critical path. On the devnet, everything below the block header is proved, but the header is the node's word. packages/lightclient only covers the Altair test cases: it has no live beacon API, Electra moves its indices, and it lacks the link from a beacon block to the execution state root.
  3. wacuum had no eth_getProof. Added on its experiment branch and checked against wac's verifier.
  4. wac's compiler miscompiles some async code. One loop silently matched nothing, so every app was refused. Rewritten, it produced a module V8 rejects. I couldn't reduce either case to a small program; the triggering file versions are in docs/wacc-cases/.
  5. The toolchain doesn't know its own identity. Nothing records the source it was built from, so I supplied it by hand. Two builds differ only by an embedded temp path. Naming it by the whole wac tree is too coarse: the hash moved when only lib.wac changed. Name it by the compiler module's hash instead.
  6. Outside projects couldn't reach mpt, ethrpc or recover (fixed on branches). Two copies of wac's library exceed the compiler's 512-file limit, so every dependency has to share one wac pin.
  7. A statement's id is the claim, not the signer. Identical claims from two signers have one id, so revocation must stay keyed by (signer, id).
  8. The first rebuild failed, usefully. The publisher's build depended on a dist/ directory only the publisher had; that is exactly what rebuilding is for.

Not done

  • The light client is not wired in (finding 2).
  • wac's own fetch and build don't enforce pins (finding 1).
  • There's no in-browser loader page or extension; a stock browser loading an HTTPS site is not protected.
  • Signing in wac is for tests only. Real signers use wallets, which tools/wallet (ethers) stands in for.
  • 0016's open questions for you (L1 or L2, EAS or our own contract, ENS or our own registry) are still open; the contract here is only a test stand-in.
